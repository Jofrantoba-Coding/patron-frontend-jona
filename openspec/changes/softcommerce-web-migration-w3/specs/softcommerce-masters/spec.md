# Spec: softcommerce-masters

NEW capability. The eight T4 masters of Wave 3 ("Nuevo" screens only), Socio acciones, and the consumers of the six pickers, each ported from its desktop `Register*` / `PanelTF*` with exact rules, messages and defaults. The mock defines the contract. Technical names (slugs, field names) are proposed by this spec.
Marker legend: **[ASSUMPTION]** = working assumption, easy to revise. **[DEVIATION]** = a desktop defect that the user decided to FIX in the web port (the fixed behavior is the spec). **[INFERRED]** = a fact the repository does not hold (stored procedures, runtime data); the spec states the chosen behavior. Wire and message conventions follow softcommerce-reference-catalogs (R-REF-2, R-REF-3: `{modo}` = `agregar` / `clonar` / `modificar` / `eliminar`; M1 `Para {modo} {entity}, debes especificar su {Campo}.`; MS `Para {modo} {entity}, debes Seleccionar {un|una} {Campo}.`). Desktop SPELLING of a message is kept (the W2 `Asignasion` precedent, for example `Trajador`, `trabajdor`); only a wrong entity or field name copied from another screen is normalized **[DEVIATION]**.

## Requirements

### R-MST-1 Scope, slugs and modes
Wave 3 MUST deliver these masters as registry entries (softcommerce-catalog-registry), each with the done bar of R-REF-1 (list with joined and formatted columns hiding inactive records, the toolbar gated by the 13 flags, the Alt shortcuts of R-CRUD-10, identical behavior against both mocks) and the modes of the desktop:

| Slug | formId | Entity | Modes | Desktop |
|---|---|---|---|---|
| `bancos` | `miBancoAnexo` | un Banco | INSERT, UPDATE, DETAIL, CLONE | PanelTFBanco / RegisterBancoAnexo |
| `trabajadores` | `miTrabajador` | un Trabajador | INSERT, UPDATE, DETAIL | PanelTFTrabajador / RegisterTrabajador |
| `vendedores` | `miVendedor` | un Vendedor | INSERT, UPDATE, DELETE, DETAIL | PanelTFVendedorNuevo / RegisterVendedor |
| `transportistas` | `miTransportista` | un Transportista | INSERT, UPDATE, DETAIL, CLONE | PanelTFTransportista / RegisterTransportistaNuevo |
| `usuarios` | `mi_usuario` | un usuario | INSERT, UPDATE, DELETE, DETAIL, CLONE | PanelTFUsuario / RegisterUsuario |
| `clientes` | `miCliente` | un Cliente | INSERT, UPDATE | PanelTFClienteNuevo / RegisterClienteNuevo |
| `proveedores` | `miProveedor` | un Proveedor | INSERT, UPDATE | PanelTFProveedorNuevo / RegisterProveedorNuevo |
| `items` | `miProducto` | un Item | INSERT, UPDATE, DELETE, DETAIL | PanelTFItem / RegisterItem |

The modes follow the desktop: a mode whose panel handler is empty or whose `executeDelete` returns `false` (Cliente, Proveedor, Trabajador, Banco, Transportista) is not offered (R-CRUD-16). Vendedor has no CLONE **[ASSUMPTION]**: its `loadRegister` disables the trabajador in every mode but INSERT, so a clone could never pick another trabajador. Menu leaves and formIds come from `MenuBarSystemDinamico`; their menu parents are proposals **[ASSUMPTION]**. The legacy `Proveedor`, `Cliente` and `Vendedor` screens, the other Item tabs and the conta `Bancos` screen (`PnlBanco` / `RegisterBanco`: a cuenta bancaria with clasificación and vendedor, a W6/W7 screen) are NOT ported; the slug `bancos` is reserved for the anexo Banco. Codes of anexo masters are 10-character zero-padded strings (R-ANX-9); the code widths of the others MUST be read from the desktop at apply time and inferred otherwise (`trabajadores` keeps its W2 width 3, `usuarios` keeps the integer id of `users.json`).

### R-MST-2 Anexo identity block (Banco, Transportista, Cliente, Proveedor)
These four masters (Chofer and Socio already have it in W2) MUST share one person block, with the entity word of the master in every message:
- Fields, in validation order: `id_tipo_doc_iden`* select over `tipos-doc-iden` where `persona` and `estado` are true (the desktop `listarTipoDocIden("", "A", "S")`; label `Tipo de Documento`); `numero_doc` (`DNI/RUC`, digits only); `ap_paterno` (U, max 50); `ap_materno` (U, max 50); `nombres` (`Nombres`, U, max 50); `descripcion` (`Razón Social`, U, max 300); `direccion` (`Dirección`, U, max 280); `sexo` opt(M:Masculino|F:Femenino) default M; `telefono` (`Telefono Fijo`, digits, max 15); `celular` (`Telefono Movil`, digits, max 15); `id_nacionalidad`* select over `nacionalidades` default `PERUANA` (label `Nacionalidad`); `email` (`E-Mail`, lowercase **[ASSUMPTION]**, no max in the desktop; max 100 **[ASSUMPTION]**).
- The tipo de documento rules are the `docIdentidad` rules of R-REF-8 unchanged: DNI (max 8, `El número de DNI que has especificado no es válida. Compruébala e inténtalo de nuevo.`, names required with `su Apellido Paterno`, `su Apellido Materno`, `su Nombre`), RUC (max 11, `El número de RUC ...`, first digit 1 = natural, 2 = juridical, otherwise the alert `EL DOCUMENTO RUC EMPIEZA CON 1 Ó 2` and the number is cleared, server hardening 422), any other tipo (max 11, razón social required), razón social composed as `{ap_paterno} {ap_materno} {nombres}` while the three names are editable, blank razón social `su Descripcion`, nacionalidad `Para {modo} {entity}, debes Seleccionar una Nacionalidad.`, tipo de documento `Para {modo} {entity}, debes Seleccionar un Tipo de Documento.`, a change of tipo clearing numero, names and razón social, and sexo shown only for natural persons. Until a tipo is chosen the number, names and razón social are disabled (Cliente, Proveedor: the form opens with no tipo; Banco, Transportista open with `RUC` selected).
- **[DEVIATION]** the desktop Banco and Transportista tipo-document message names `un Cliente`; it names the real entity. **[DEVIATION]** the desktop Banco and Transportista UPDATE forces nacionalidad `PERUANA`; the stored nacionalidad and tipo de documento are restored.
- Each master MUST store `flag_tipo_persona` = `J` when the tipo is RUC (id `05`) and the first digit is `2`, otherwise `N` (R-REF-8; Proveedor computes it in the desktop, **[INFERRED]** for the others) and its hidden tipo anexo (R-ANX-9). `Estado` is derived from the activation (R-ACT-5) and every master of this block carries the shared activation tab (R-ANX-1) and `Activación de {Entidad}` title.
- The server MUST apply the same rules to every write (R-MOCK-10), checking required fields and the `docIdentidad` steps in the declared order and stopping at the first failure (D10). No uniqueness is applied to (tipo, número) **[ASSUMPTION]** (W2 Chofer / Socio precedent; the desktop procedure is not in the repository).

### R-MST-3 Banco
`bancos` MUST be the identity block of R-MST-2 (entity `un Banco`: `Para {modo} un Banco, debes especificar su Apellido Paterno.`, `... su Nombre.`, `... su Descripcion.`, `... Seleccionar una Nacionalidad.`) plus the shared activation tab. Its list shows the code, the razón social (or full name), tipo and número de documento and the estado. **[DEVIATION]** the desktop `RegisterBancoAnexo` also loads and sends padrón flags (`flagpercepcion`, `flagretencion`, `flagExceptuado`) although it has no padrón tab; they are not ported. It is the pilot of the shared Anexo grid (R-ANX-1) and of G11 / G12.

### R-MST-4 Trabajador
`trabajadores` MUST replace the W2 minimal lookup by a full master (the lookup slug, row shape `{ id_trabajador, nombre }` and filters of R-REF-11 stay, R-MST-17), with the fields below in validation order and the desktop literal messages (no M1 template):
- `id_tipo_trabajador`* select over active `tipos-trabajador` (`Tipo Trabajador`): `Seleccione Tipo Trabajador`.
- `id_tipo_perfil`* select over `tipos-trabajador-perfil` of that tipo (`Trabajador Perfil`; disabled and empty until the tipo is chosen, R-CRUD-12): `Seleccione Trabajador Perfil`.
- `ap_paterno`* (`Ap Paterno`, U, max 50): `Ingrese Apellido Paterno`; `ap_materno`* (`Ap Materno`, U, max 50): `Ingrese Apellido Materno`; `nombres`* (`Nombres`, U, max 50): `Ingrese Nombres`.
- `dni`* (`Dni`, digits, max 10): `Ingrese Dni` (no 8-digit minimum, as the desktop).
- `fecha_nac`* date `dd/MM/yyyy` (`Fecha Nac`, default today; blank or invalid): `La fecha que has especificado no es válida. Compruébala e inténtalo de nuevo.`
- Optional: `direccion` (`Direccion`, max 300), `email` (`Email`, max 50) (**[ASSUMPTION]** the desktop `setDocument` limits are commented out; these are the commented values), `sexo` opt(M:Masculino|F:Femenino) default M, `telefono` (`Telf Fijo`, digits, max 10), `celular` (`Telf Movil`, digits, max 10).
`nombre` (the lookup display) is derived by the server as `{nombres} {ap_paterno} {ap_materno}` **[ASSUMPTION]** (the order of the W2 seed `JUAN PEREZ LOPEZ`). The register has the shared activation tab (`Activación de Trabajador`, entity word `Trabajador`) and `Estado` is derived (R-ACT-5); the Trabajador is the first G12 consumer. The perfil of the trabajador is the perfil that governs the grants of the user linked to it (R-PRM-5, R-AUTH-11).

### R-MST-5 Transportista
`transportistas` MUST be the identity block of R-MST-2 (entity `un Transportista`) opening with tipo `RUC` selected, plus the shared activation tab and a `Vehiculos` grid. The vehicle entry is inline above the grid (fields `Constancia`, `Placa`, `Peso`, `Marca`, `Modelo` and the buttons `Agregar` / `Quitar`; R-MD-3 `inline`):
- `Agregar` validates in this order with these messages: blank constancia `Ingrese Constancia`, blank placa `Ingrese Placa`, blank peso `Ingrese Peso`, no marca `Seleccione Marca`, no modelo `Seleccione Modelo`; limits and normalization of the W2 `vehiculos` entry (constancia and placa uppercase max 30, peso digits max 10 default `0`, marca and modelo over the active `marcas-vehiculo` / `modelos-vehiculo`); a valid add appends a pending row (estado active) and resets the entry fields (peso `0`).
- `Quitar` confirms `Desea Quitar el Vehiculo?`, shows `Seleccione Vehiculo` with no selection, removes a pending row, and for a persisted row removes it from the grid and logically deletes it on save (kind `delete`, R-MD-4).
The Transportista screen has no DELETE; its `Estado` is derived.

### R-MST-6 Vehiculos shared store and the propietario picker (W2b leftover)
The Transportista `Vehiculos` grid and the W2 `vehiculos` catalog MUST read and write the SAME records (one store): the grid shows the vehiculos whose propietario is that transportista. The W2 `vehiculos` entry MUST gain the optional `id_anexo_empresa_transportista` (`Propietario`) as a `lookup` field over `transportistas` (active only; typed-code resolution R-LKP-6; the desktop buscaba tipo anexo `6`), shown in the register and the list. A vehicle created from the W2 screen with propietario X MUST appear in X's grid and one created from X's grid MUST carry X as propietario. Propietario stays optional (the desktop `RegisterVehiculo.isRegisterValid` does not check it); a propietario that is not an active transportista answers 422 on that field. The W2 Vehiculo scenarios (S-REF-31) pass unchanged.

### R-MST-7 Usuario
`usuarios` MUST replace the W2 read-only projection by a writable master whose rows remain the `users.json` records (R-AUTH-10). Fields, validation order and messages (entity `un usuario`, lowercase; `{modo}` as above):
1. `id_trabajador`* `lookup` over `trabajadores` (BuscarTrabajador, label `Trabajador`): `Para {modo} un usuario, debes especificar un Trajador.` (spelling kept). The register shows the trabajador name and its `Cargo` (tipo de trabajador) read-only once chosen.
2. `usuario`* (`Nombre de Usuario`, max 50): `Para {modo} un usuario, debes especificar su nombre.`
3. `clave`* password with confirmation (R-CRUD-17; `Contraseña`, max 20): `Para {modo} un usuario, debes especificar su clave.`
4. Flags `Escritorio`, `Web`, `Contable` and `Habilitado`, all default OFF on INSERT (the desktop `newRegister` unchecks them: a new user can log in only after an administrator ticks `Habilitado` and `Escritorio`).
`nombre` (the `usuarios` lookup display) MUST be derived from the chosen trabajador's `nombre`, keeping the W2 row shape `{ id_usuario, usuario, nombre }` (R-MST-17). The stored flags follow `users.json`: `flaghabilitado` `A` enabled / `D` disabled (the desktop stores `H` / `D`; **[INFERRED]** the mock uses its own `A` convention, R-AUTH-4) and `flagEscritorio` / `flagWeb` / `flagContable` `S` / `N`. The legacy `modificar`, `eliminar`, `insertar` user flags are hidden in the desktop and are stored as `N`. The tenants of a new user MUST be the session tenant. A duplicate `usuario` within the tenant MUST answer 409 `DUPLICATE` on `usuario` **[ASSUMPTION]** with the NEW text `El nombre de usuario ya existe.` (the desktop message comes from a stored procedure not in the repository; the login needs the name to be unique). DELETE is the logical delete of R-MOCK-7 and also removes the user's series authorizations (R-MD-7). CLONE copies the fields except the code and the password **[DEVIATION]** (the desktop copied the decrypted password). The list toolbar has the extra `Autorizar Series` action (R-PRM-6). The desktop `Nuevo Trabajador` button (`cbNuevoTrabajador`) is not ported **[ASSUMPTION]** (the "create related" exclusion of R-REF-12).

### R-MST-8 Usuario credentials
On INSERT and CLONE the password and its confirmation MUST be required. On UPDATE a blank password MUST keep the stored one **[DEVIATION]** (the desktop displayed the decrypted password and required it again; the server never returns it, R-MOCK-23). A password longer than 20 characters MUST be rejected by input (S-CRUD-14) and by the server (422 on `clave`). A confirmation different from the password MUST block submit with an error on the confirmation field and the server MUST answer 422 on `clave_confirmacion` for a body whose confirmation differs. No list, get, lookup or error response MAY ever contain the password (R-AUTH-12). The desktop `Mostrar caracteres` toggle is ported as a show / hide control of the field.

### R-MST-9 Vendedor
`vendedores` MUST be one anexo of tipo 8 built from a trabajador:
- `Cargar Trabajador` (button `Buscar`) opens the PanelCargarTrabajador picker (R-LKP-7); the picked trabajador fills `Nombres`, `Dirección`, `Numero` (its DNI), `Telefono Fijo`, `Telefono Movil` and `Codigo Trab.`; `Nombres`, `Dirección` and `Numero` are then read-only. In every mode but INSERT the picker and those fields are disabled.
- Fields: `Tipo de Documento` (default DNI, id `01`; **[DEVIATION]** the desktop hardcodes id `01` on save and drops the last tipo of the combo; the selected tipo is stored and no entry is dropped), `Numero` (max 8 for DNI, 11 for RUC), `Nacionalidad` default `PERUANA`, `Credito` and `Contado` checkboxes (`Contado` default checked, `Credito` unchecked), `Comentario` (textarea, optional **[DEVIATION]**: the desktop shows it but never saves it; it is stored, max 500 **[ASSUMPTION]**).
- The only validation is a chosen trabajador: `Debe elegir un trabajdor` (spelling kept), shown on the `Nombres` field.
- It has the shared activation tab (`Activación de Vendedor`) and a derived `Estado` (R-ANX-6, R-ACT-5). Its list columns are `COD`, `NOMBRES`, `DNI`, `DIRECCION`, `TELEFONO`, `CREDITO`, `CONTADO`, `ESTADO`. DELETE cascades to the activation rows (R-MD-7).
- A vendedor MAY be referenced by W4 sales; no uniqueness of the trabajador is applied **[ASSUMPTION]** (procedure not in the repository).

### R-MST-10 Cliente (general)
`clientes` MUST be the identity block of R-MST-2 (entity `un Cliente`; no default tipo; messages `Para {modo} un Cliente, debes ...`) plus:
- `id_clasif_cliente`* select over active `clasif-clientes` (`Tipo Cliente`, first option `--- Seleccione Tipo ---`): `Para {modo} un Cliente, debes Seleccionar un Tipo de Cliente.`, checked after the razón social and skipped when the selected tipo de documento has abreviatura `OTROS` (**[INFERRED]** no seeded tipo is `OTROS`).
- When the company parameter `IS_CLIENTE_CONDICION_PAGO` is true: `Condicion Pago` select (`CONTADO` / `CREDITO`) and `Numero de dias` (digits, max 3; enabled only for CREDITO; reset to `0` on every change of the condición); a blank número de días blocks submit with `Ingrese numero de Dias` (checked last). The condición is stored as `flag_contado` / `flag_credito` `S` / `N` and the días. **[INFERRED]** the values of the desktop `CondicionPagoEnum`.
- `Credito` and `Credito Temp` totals (read-only, default `0`) shown only with the credit tabs (R-MST-12).
- Tabs, in order: `General`, `Activación de Cliente`, `Direcciones`, `Sustitutos` (param), `Credito` and `Credito Temp` (param), `Padrones`, `Contactos`, `Cuentas`. The list columns include `COD`, `T_PERSONA`, `RAZON SOCIAL`, `PATERNO`, `MATERNO`, `NOMBRES`, `RUC/DNI`, `DIRECCION`, and, with the parameters, `CANT_SUST`, `CONDICION PAGO`, `NUMERO DIAS`.
- The padrón flags are derived (R-ANX-8). The client row for the picker consumers (BuscarCliente, FormClienteBuscar) is this master.

### R-MST-11 Cliente child grids: Direcciones, Contactos, Cuentas
- **Direcciones** (`Agregar Direccion`, kind `deactivate`): `Departamento`, `Provincia`, `Distrito` (the ubigeo cascade of R-LOC-4, as one cascade), `Zona` (select over active `zonas` of the chosen distrito) and `Direccion` (U). Order and messages: `Debes Seleccionar un Departamento.`, `Debes Seleccionar una Provincia.`, distrito `Debes Seleccionar un Distrito.` **[DEVIATION]** (the desktop says `un Almacen`), `Debes Seleccionar una Zona.` (only when the parameter `IS_DIRECCION_CLIENTE` is false; with it true, the default, the zona is optional and the ubigeo cascade offers every ubigeo, with it false the cascade offers only ubigeos having an active zona, `filter { has: 'zonas' }`, **[INFERRED]** from `loadUbigeo(..., !IS_DIRECCION_CLIENTE)`), `Debes Ingresar Direccion.` Grid: estado, distrito, zona, dirección. `Quitar`: `Direccion ya Esta desactivada`, `Desea Quitar Direccion?`, `Para quitar una direccion primero debe seleccionar la fila.` (title `Quitar Direccion`).
- **Contactos** (`Agregar Contacto`, kind `deactivate`): `Paterno`* (U, max 50) `Ingrese Apellido Paterno`; `Materno`* (U, max 50) `Ingrese Apellido Materno`; `Nombres`* (U, max 50) `Ingrese Nombres`; `Correo`; `Telef` (digits, max 15); `Celular` (digits, max 15). `Quitar`: `Contacto ya esta Desactivado`, `Desea Quitar Contacto?`, `Seleccione Fila.` (title `Quitar Contacto`).
- **Cuentas** (`Agregar Cuenta`, kind `deactivate`): `Banco`* select over the active `tablas-detalle-sunat` rows of tabla `3` (`--- Seleccione un Banco ---`; **[INFERRED]** tabla `3` = the bank table); `Nombre` (disabled and filled with the banco name; editable and cleared only when the banco is the detalle `58`, **[INFERRED]** "otros"); `Cuenta`* (número). Order and messages: `Seleccione Banco`, `Ingrese Nombre de Banco`, `Ingrese Numero de Cuenta`. `Quitar`: `Cuenta ya esta Desactivada`, `Desea Quitar Cuenta?`, `Seleccione Fila.` (title `Quitar Cuenta`). **[DEVIATION from the proposal premise]** the Cliente `Cuenta` is a BANK account over `tablas-detalle-sunat`, NOT a cuenta contable: the cuentas-contables stub (R-MOCK-25) is not needed by the Cliente.

### R-MST-12 Cliente parameter-gated tabs: Sustitutos, Credito, Condición de pago
These tabs MUST be present only when the company parameter is true (R-MOCK-24); the seeded `demo` tenant MUST enable them so they are reachable and tested **[ASSUMPTION]**.
- **Sustitutos** (`IS_CLIENTE_SUSTITUTO`; desktop default false): `Agregar` opens FormClienteBuscar (R-LKP-7); rows show estado and cliente; `Activar` (`Sustituto ya esta activado`, `Cliente esta desactivado`, confirm `Desea activar Cliente Sustituto?`), `Desactivar` (`Sustituto ya esta desactivado`, confirm `Desea Desactivar Cliente Sustituto?`; a pending row is removed, a persisted one is deactivated); no selection `Seleccionar un Elemento.` (title `Quitar Sustituto`). A sustituto is unique among active rows (`Cliente ya Esta Agregado`, R-MD-6). The list column `CANT_SUST` counts the active sustitutos.
- **Credito** and **Credito Temp** (`IS_CLIENTE_CREDITO`; **[INFERRED]** no desktop code ever sets it, so the desktop default false makes both tabs unreachable there; they are ported behind the parameter): the dialog asks `Motivo`* (U, max 50) `Ingrese Motivo`, `Monto`* (decimal) `Ingrese Monto`, `F Inicio` (default today) and, for the temporal credit only, `F Fin` (default today). **[DEVIATION]** the desktop copies the fecha de INICIO into the fin of a temporal credit (`dc_fechainicio.getDate()` used for both) and validates no dates; the fin is stored as entered and a fin before the inicio is refused with `Fecha es menor a fecha inicial`. Credit rows are additive (the desktop has no deactivate action for them); `Credito` / `Credito Temp` show the sum of the montos of the rows of their kind.

### R-MST-13 Proveedor
`proveedores` MUST be the identity block of R-MST-2 (entity `un Proveedor`; no default tipo; `Para {modo} un Proveedor, debes ...`) plus the shared activation tab (`Activación de Proveedor`) and the `Padrones` tab (R-ANX-7; offers `02`, `03`, `04`). Its modes are INSERT and UPDATE. **[DEVIATION from the proposal premise]** `FormDireccionProveedor`, `FormConfigPadronProveedor` and `FormPanelConfigPadronProveedor` are instantiated only by the legacy `RegisterProveedor`, not by `RegisterProveedorNuevo` (whose tabs are `General`, `Activación de Proveedor` and `Padrones`); they are not ported, the address is the `Dirección` text field of the identity block, and the padrón configuration is the padrón grid. Its list columns are `COD`, `T_PERSONA`, `RAZON SOCIAL`, `PATERNO`, `MATERNO`, `NOMBRES`, `RUC/DNI`, `DIRECCION`.

### R-MST-14 Item (MVP): identity, classification, units and tax
`items` MUST cover, from `RegisterItem`, the tab `Datos de Item` with these fields (entity `un Item`; validation order and messages as listed; the others are optional):
1. `id_alterno`* (`Cod. Alterno`, U, max 30): `Para {modo} un Item, debes especificar su Codigo Alternativo.`
2. `id_familia`* select over the session empresa's active `familias`: `... debes especificar su Familia.`
3. `id_marca`* select over active `marcas` (`--- Seleccione una Marca ---`): `... su Marca.`
4. `descripcion`* (`Descripción`, U, max 255): `... su Descripcion.`
5. `id_um_stock`* (`U. Stock`) select over active `unidades-medida` shown by abreviatura (`--- Seleccione U.M. ---`): `... su U. Stock.`
6. `id_um_compra`* (`U. Compra`): `... su U. Compra.` and 7. `id_um_venta`* (`U. Venta`): `... su U. Venta.`. Choosing `U. Stock` sets `U. Compra` and `U. Venta` to the same unit and both are read-only (the desktop disables them).
Optional: `id_subfamilia` select ← familia (`SubFamilia`; disabled and empty until a familia is chosen; changing the familia clears and reloads it), `id_tamano` (`Tamaño`, `--- Seleccione un Tamaño ---`), `id_color` (`Grupo`), `codigo_clase_sunat` (`Codigo Sunat`, options depend on the chosen subfamilia's SUNAT code and are empty without one; source `clases-sunat`, a read-only stub, R-MOCK-25), `codigo_barras` (`Cod. Barras`), `tipo` opt(P:Producto|C:Concepto|T:Transporte) default `P` (`Tipo`), `perecible` radio (`Perecible` / `No perecible`, default no) with `dias` (`dias |`, digits, max 10, default `0`) shown only for tipo `P`, `afecto_igv` opt(AFECTO|INAFECTO|EXONERADO) default `AFECTO` (`Afecto a IGV`), `por_igv` (`Porc. IGV`, decimal: with AFECTO editable and defaulting to the company IGV percentage, with another option read-only `0`), `stock_min` (`Stock Min`, decimal, default `0`), `estado` (`Item Activo`, default checked, editable) and, only when the company parameter `ISBOTICA` or `IS_BOTICA_SIN_LOTE` is true, `composicion` (`Composicion`) and `funcion` (`Funcion`) (U, max 255). `Kardex` and `Serv.Transporte` are derived read-only from the tipo (`P`: kardex on; `C`: both off; `T`: transporte on), and a change of tipo resets perecible to `No perecible` and dias to `0`. `Suj. Percepción` and `Porc. Perc` are read-only (the Percepción tab is deferred, R-MST-15).
**[INFERRED]** the uniqueness of `id_alterno` and the server item code are stored-procedure rules not in the repository; the mock applies `unique (id_alterno)` per tenant **[ASSUMPTION]** with a NEW message `El codigo alternativo ya existe.` and a generated code.

### R-MST-15 Item (MVP): almacenes, prices and deferred tabs
- The `Configuracion Almacen` tab holds the child grid `Almacenes` (kind `deactivate`): `Agregar` opens a dialog with `Localidad` (`--- Seleccione una Localidad ---`, of the session empresa), `Pto Venta` ← localidad, `Almacen` ← punto de venta, `Proceso` opt(VENTA|DESPACHO) and `Fecha Inicio` (default today). Order and messages: `Seleccione Localidad`, `Seleccione Punto de Venta`, `Seleccione Almacen`, `Seleccione Proceso`; a duplicate active (almacén, proceso) in the grid answers `Almacen ya se Encuentra Activado`. A pending row is estado active; `Quitar` follows R-MD-4.
- The six prices `Precio Soles` (`Tarjeta`, `Publico`, `Mayor`) and `Precio Dolares` (`Tarjeta`, `Publico`, `Mayor`) (decimals, no validation, a blank is `0`, **[INFERRED]**) MUST be shown only when the company parameter `IS_ITEM_RESUMEN_PRECIO` is true (the desktop gates them by `IS_ITEM_BY_CLIENTE || IS_ITEM_RESUMEN_PRECIO`; the `Moneda` select belongs to `IS_ITEM_BY_CLIENTE` and is not ported) and stored per item for the session empresa; the seeded `demo` tenant enables the parameter **[ASSUMPTION]**.
- DELETE of an Item cascades to its almacén rows (R-MD-7). CLONE is not offered.
- Deferred (NOT in W3, no tab, no code): `Conversion a Item`, `Caracteristicas del Item`, `Configuracion Item`, `Descuento Item`, `Configuracion Cuenta`, `Percepcion`, `Promociones`, and the dialogs FormItemCaracteristica, FormItemConfig, FormItemConfigDscto, FormItemConfigCuenta, FormItemPercepcion. BuscarItemConversion is built as a picker (R-LKP-7) with a harness host because its only desktop consumer is the deferred `Conversion a Item` tab.

### R-MST-16 Socio acciones
`socio-acciones` (formId `miAccionSocio`) MUST be one modal screen (no list) with the tabs `Socios` and `Precio`, the buttons `Aceptar` and `Cancelar`, and the `Activar` / `Desactivar` actions of each tab (`deferred`, R-ACT-4: nothing is persisted before `Aceptar`). It MUST be last in the Wave 3 order.
- **Precio**: grid of price rows (estado, fecha inicio, fecha fin, precio **[INFERRED]**). `Activar` is refused with `No se Puede Agregar mas de un Precio` when a price is active; its dialog `Activar Precio` asks `Precio`* (decimal) `Ingrese Precio` and `Fecha Inicio` (default today). A new price MUST be applied to every ACTIVE socio row of the `Socios` tab. `Desactivar` requires a selected row (`Seleccionar Fila`, title `Precio`), refuses a deactivated one (`Precio Seleccionado ya esta desactivado`), confirms `Desea Desactivar Precio?` and opens `Desactivar Precio` asking only `Fecha Fin` (default today) **[DEVIATION]** (the desktop also demands `Precio` there). **[DEVIATION]** a fecha fin that is not after the price's fecha inicio is refused with `Fecha es menor a fecha inicial` (the desktop showed it without blocking).
- **Socios**: grid of socio rows (estado, socio, fecha inicio, fecha fin, precio, cantidad **[INFERRED]**). `Activar` opens the dialog `Activar Socio` over the active `socios` with the filters `Código` (digits, max 10), `DNI/RUC` (digits, max 11) and `R. Social` (U, max 100) (R-LKP-2), `Cantidad`* (decimal) `Ingrese Cantidad`, `Fecha Inicio` (default today) and `Aceptar` / `Refrescar` / `Cancelar`; a confirm without a selected socio shows `Seleccione un registro de la tabla`; a socio already active shows `Socio ya esta activado`. A new socio row takes the current active price (`0` with none). `Desactivar` sets the selected row deactivated with a `Fecha Fin` **[INFERRED]** (the desktop handler is outside the read set; it mirrors Precio).
- `Aceptar` MUST refuse with `Ingrese Precio` when there is no active price; otherwise it saves precios and socios as one operation, shows the server message and closes. The server MUST answer the same checks (422).

### R-MST-17 Lookup replacement and consumers
The `usuarios` and `trabajadores` entries become writable masters without changing their lookup contract: `GET /v1/lookups/usuarios` and `GET /v1/lookups/trabajadores` return `{ items: [{ id, name }] }` of ACTIVE records, `GET /v1/usuarios` and `GET /v1/trabajadores` keep their W2 row keys (`id_usuario`, `usuario`, `nombre`; `id_trabajador`, `nombre`), and every W2 consumer keeps its W2 scenarios (S-REF-17, S-REF-21) with the same meaning. UsuarioCorrelativo keeps its `usuario` as a select; TrabajadorPuntoVenta moves to the BuscarTrabajador lookup (R-LKP-8), which forces the documented W2-test exception of R-MST-18. A master replacement MUST be preceded by parity tests (the W2 suites) in the same PR.

### R-MST-18 Done bar, parity and tests
Every master and child MUST satisfy the done bar of R-REF-1, with table-driven tests generated from its registry entry (required, max length, normalization, ranges, uniqueness, conditional, chain, child rules) running against both mocks through the same `InterCatalogService` (R-REF-13, R-MOCK-18), and every message of this spec MUST have at least one test. The W1 and W2 suites MUST pass unchanged except the amendments listed in softcommerce-reference-catalogs and softcommerce-auth-session and the following W2-test exceptions (S-CRUD-39 style; every other assertion stays identical):
1. `src/catalogs/registry.trabajadorPuntoVenta.ui.spec.tsx`: the field helpers that drive the `id_trabajador` `select` change to drive the `lookup` field (open dialog, pick row); assertions of S-REF-21 are unchanged.
2. The W1 / W2 suites that pin `usuarios` / `trabajadores` as read-only lookups (405 on write): the read-only expectation changes to the writable-master expectation of S-REF-43; their GET / lookup assertions are unchanged.
