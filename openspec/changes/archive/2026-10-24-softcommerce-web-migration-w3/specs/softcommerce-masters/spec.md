# Spec: softcommerce-masters

NEW capability. The eight T4 masters of Wave 3 ("Nuevo" screens only), Socio acciones, and the consumers of the six pickers, each ported from its desktop `Register*` / `PanelTF*` with exact rules, messages and defaults. The mock defines the contract. Technical names (slugs, field names) are proposed by this spec.
Marker legend: **[ASSUMPTION]** = working assumption, easy to revise. **[DEVIATION]** = a desktop defect that the user decided to FIX in the web port (the fixed behavior is the spec). **[INFERRED]** = a fact the repository does not hold (stored procedures, runtime data); the spec states the chosen behavior. Wire and message conventions follow softcommerce-reference-catalogs (R-REF-2, R-REF-3: `{modo}` = `agregar` / `clonar` / `modificar` / `eliminar`; M1 `Para {modo} {entity}, debes especificar su {Campo}.`; MS `Para {modo} {entity}, debes Seleccionar {un|una} {Campo}.`). Desktop SPELLING of a message is kept (the W2 `Asignasion` precedent, for example `Trajador`, `trabajdor`); only a wrong entity or field name copied from another screen is normalized **[DEVIATION]**.

## Requirements

### R-MST-1 Scope, slugs and modes
Wave 3 MUST deliver these masters as registry entries (softcommerce-catalog-registry), each with the done bar of R-REF-1 (list with joined and formatted columns hiding inactive records, the toolbar gated by the 13 flags, the Alt shortcuts of R-CRUD-10, identical behavior against both mocks) and the modes of the desktop:

| Slug | formId | Entity | Modes | Desktop |
|---|---|---|---|---|
| `bancos` | `miBancoAnexo` | un Banco | INSERT, UPDATE, DETAIL, CLONE | PanelTFBanco / RegisterBancoAnexo |
| `trabajadores` | `miTrabajador` | un Trabajador | INSERT, UPDATE, DETAIL | PanelTFTrabajador / RegisterTrabajador |
| `vendedores` | `miVendedor` | un Vendedor | INSERT, UPDATE, DELETE, DETAIL | PanelTFVendedorNuevo / RegisterVendedor |
| `transportistas` | `miTransportista` | un Transportista | INSERT, UPDATE, DETAIL, CLONE | PanelTFTransportista / RegisterTransportistaNuevo |
| `usuarios` | `mi_usuario` | un usuario | INSERT, UPDATE, DELETE, DETAIL, CLONE | PanelTFUsuario / RegisterUsuario |
| `clientes` | `miCliente` | un Cliente | INSERT, UPDATE | PanelTFClienteNuevo / RegisterClienteNuevo |
| `proveedores` | `miProveedor` | un Proveedor | INSERT, UPDATE | PanelTFProveedorNuevo / RegisterProveedorNuevo |
| `items` | `miProducto` | un Item | INSERT, UPDATE, DELETE, DETAIL | PanelTFItem / RegisterItem |

The modes follow the desktop: a mode whose panel handler is empty or whose `executeDelete` returns `false` (Cliente, Proveedor, Trabajador, Banco, Transportista) is not offered (R-CRUD-16). Vendedor has no CLONE **[ASSUMPTION]**: its `loadRegister` disables the trabajador in every mode but INSERT, so a clone could never pick another trabajador. Menu leaves and formIds come from `MenuBarSystemDinamico`; their menu parents are proposals **[ASSUMPTION]**. The legacy `Proveedor`, `Cliente` and `Vendedor` screens, the other Item tabs and the conta `Bancos` screen (`PnlBanco` / `RegisterBanco`: a cuenta bancaria with clasificación and vendedor, a W6/W7 screen) are NOT ported; the slug `bancos` is reserved for the anexo Banco. Codes of anexo masters are 10-character zero-padded strings (R-ANX-9); the code widths of the others MUST be read from the desktop at apply time and inferred otherwise (`trabajadores` keeps its W2 width 3, `usuarios` keeps the integer id of `users.json`).

### R-MST-2 Anexo identity block (Banco, Transportista, Cliente, Proveedor)
These four masters (Chofer and Socio already have it in W2) MUST share one person block, with the entity word of the master in every message:
- Fields, in validation order: `id_tipo_doc_iden`* select over `tipos-doc-iden` where `persona` and `estado` are true (the desktop `listarTipoDocIden("", "A", "S")`; label `Tipo de Documento`); `numero_doc` (`DNI/RUC`, digits only); `ap_paterno` (U, max 50); `ap_materno` (U, max 50); `nombres` (`Nombres`, U, max 50); `descripcion` (`Razón Social`, U, max 300); `direccion` (`Dirección`, U, max 280); `sexo` opt(M:Masculino|F:Femenino) default M; `telefono` (`Telefono Fijo`, digits, max 15); `celular` (`Telefono Movil`, digits, max 15); `id_nacionalidad`* select over `nacionalidades` default `PERUANA` (label `Nacionalidad`); `email` (`E-Mail`, lowercase **[ASSUMPTION]**, no max in the desktop; max 100 **[ASSUMPTION]**).
- The tipo de documento rules are the `docIdentidad` rules of R-REF-8 unchanged: DNI (max 8, `El número de DNI que has especificado no es válida. Compruébala e inténtalo de nuevo.`, names required with `su Apellido Paterno`, `su Apellido Materno`, `su Nombre`), RUC (max 11, `El número de RUC ...`, first digit 1 = natural, 2 = juridical, otherwise the alert `EL DOCUMENTO RUC EMPIEZA CON 1 Ó 2` and the number is cleared, server hardening 422), any other tipo (max 11, razón social required), razón social composed as `{ap_paterno} {ap_materno} {nombres}` while the three names are editable, blank razón social `su Descripcion`, nacionalidad `Para {modo} {entity}, debes Seleccionar una Nacionalidad.`, tipo de documento `Para {modo} {entity}, debes Seleccionar un Tipo de Documento.`, a change of tipo clearing numero, names and razón social, and sexo shown only for natural persons. Until a tipo is chosen the number, names and razón social are disabled (Cliente, Proveedor: the form opens with no tipo; Banco, Transportista open with `RUC` selected).
- **[DEVIATION]** the desktop Banco and Transportista tipo-document message names `un Cliente`; it names the real entity. **[DEVIATION]** the desktop Banco and Transportista UPDATE forces nacionalidad `PERUANA`; the stored nacionalidad and tipo de documento are restored.
- Each master MUST store `flag_tipo_persona` = `J` when the tipo is RUC (id `05`) and the first digit is `2`, otherwise `N` (R-REF-8; Proveedor computes it in the desktop, **[INFERRED]** for the others) and its hidden tipo anexo (R-ANX-9). `Estado` is derived from the activation (R-ACT-5) and every master of this block carries the shared activation tab (R-ANX-1) and `Activación de {Entidad}` title.
- The server MUST apply the same rules to every write (R-MOCK-10), checking required fields and the `docIdentidad` steps in the declared order and stopping at the first failure (D10). No uniqueness is applied to (tipo, número) **[ASSUMPTION]** (W2 Chofer / Socio precedent; the desktop procedure is not in the repository).

### R-MST-3 Banco
`bancos` MUST be the identity block of R-MST-2 (entity `un Banco`: `Para {modo} un Banco, debes especificar su Apellido Paterno.`, `... su Nombre.`, `... su Descripcion.`, `... Seleccionar una Nacionalidad.`) plus the shared activation tab. Its list shows the code, the razón social (or full name), tipo and número de documento and the estado. **[DEVIATION]** the desktop `RegisterBancoAnexo` also loads and sends padrón flags (`flagpercepcion`, `flagretencion`, `flagExceptuado`) although it has no padrón tab; they are not ported. It is the pilot of the shared Anexo grid (R-ANX-1) and of G11 / G12.

### R-MST-4 Trabajador
`trabajadores` MUST replace the W2 minimal lookup by a full master (the lookup slug, row shape `{ id_trabajador, nombre }` and filters of R-REF-11 stay, R-MST-17), with the fields below in validation order and the desktop literal messages (no M1 template):
- `id_tipo_trabajador`* select over active `tipos-trabajador` (`Tipo Trabajador`): `Seleccione Tipo Trabajador`.
- `id_tipo_perfil`* select over `tipos-trabajador-perfil` of that tipo (`Trabajador Perfil`; disabled and empty until the tipo is chosen, R-CRUD-12): `Seleccione Trabajador Perfil`.
- `ap_paterno`* (`Ap Paterno`, U, max 50): `Ingrese Apellido Paterno`; `ap_materno`* (`Ap Materno`, U, max 50): `Ingrese Apellido Materno`; `nombres`* (`Nombres`, U, max 50): `Ingrese Nombres`.
- `dni`* (`Dni`, digits, max 10): `Ingrese Dni` (no 8-digit minimum, as the desktop).
- `fecha_nac`* date `dd/MM/yyyy` (`Fecha Nac`, default today; blank or invalid): `La fecha que has especificado no es válida. Compruébala e inténtalo de nuevo.`
- Optional: `direccion` (`Direccion`, max 300), `email` (`Email`, max 50) (**[ASSUMPTION]** the desktop `setDocument` limits are commented out; these are the commented values), `sexo` opt(M:Masculino|F:Femenino) default M, `telefono` (`Telf Fijo`, digits, max 10), `celular` (`Telf Movil`, digits, max 10).
`nombre` (the lookup display) is derived by the server as `{ap_paterno} {ap_materno} {nombres}` (`RegisterTrabajador.getBeanTrabajador`: `paterno + " " + materno + " " + nombres`, each part trimmed; **[DEVIATION]** from the first assumption, the order of the W2 seed `JUAN PEREZ LOPEZ`, which only the seed rows keep until they are edited). The rule `nombreCompuesto` hides it from the register and owns it. The code is padded to three, like the W2 seed codes (**[DEVIATION]**: `PanelTFTrabajador.focusLost` pads to five, but a typed code of the BuscarTrabajador lookup must still resolve the seeded `001`); the tipo anexo is the placeholder `9` **[INFERRED]**; `mantTrabajador` stamps the session user and empresa. The register has the shared activation tab (`Activación de Trabajador`, entity word `Trabajador`) and `Estado` is derived (R-ACT-5); the Trabajador is the first G12 consumer. The perfil of the trabajador is the perfil that governs the grants of the user linked to it (R-PRM-5, R-AUTH-11).

### R-MST-5 Transportista
`transportistas` MUST be the identity block of R-MST-2 (entity `un Transportista`) opening with tipo `RUC` selected, plus the shared activation tab and the `Vehiculo` tab (the desktop tab title; **[DEVIATION]** none, the spec called it `Vehiculos`) holding the `Vehiculos` grid with the columns `CODIGO`, `PLACA`, `CONSTANCIA INSCRIPCION`, `MARCA` and `MODELO` (the other `VehiculoTableModel` columns are hidden; a pending row shows the marca and modelo names too). The vehicle entry is inline above the grid (fields `Constancia`, `Placa`, `Peso`, `Marca`, `Modelo` and the buttons `Agregar` / `Quitar`; R-MD-3 `inline`):
- `Agregar` validates in this order with these messages: blank constancia `Ingrese Constancia`, blank placa `Ingrese Placa`, blank peso `Ingrese Peso`, no marca `Seleccione Marca`, no modelo `Seleccione Modelo`; limits and normalization of the W2 `vehiculos` entry (constancia and placa uppercase max 30, peso digits max 10 default `0`, marca and modelo over the active `marcas-vehiculo` / `modelos-vehiculo`); a valid add appends a pending row (estado active) and resets the entry fields (peso `0`).
- `Quitar` confirms `Desea Quitar el Vehiculo?`, shows `Seleccione Vehiculo` with no selection, removes a pending row, and for a persisted row removes it from the grid and logically deletes it on save (kind `delete`, R-MD-4).
The Transportista screen has no DELETE; its `Estado` is derived. *Applied in W3-10:* the child is `store: { entry: 'vehiculos', key: 'id_anexo_empresa_transportista' }` with `entryFields` (R-REG-14) naming the five entry fields in the order `Const inscripcion`, `Placa`, `Peso(KG)`, `Marca`, `Modelo` and their sentences; the nested route and the W2 route answer with their own sentences (the W2 `vehiculos` entry is unchanged), and the parent key is never ref-checked on a nested write, so a deactivated transportista still takes vehicles in its grid.

### R-MST-6 Vehiculos shared store and the propietario picker (W2b leftover)
The Transportista `Vehiculos` grid and the W2 `vehiculos` catalog MUST read and write the SAME records (one store): the grid shows the vehiculos whose propietario is that transportista. The W2 `vehiculos` entry MUST gain the optional `id_anexo_empresa_transportista` (`Propietario`) as a `lookup` field over `transportistas` (active only; typed-code resolution R-LKP-6; the desktop buscaba tipo anexo `6`), shown in the register and the list. A vehicle created from the W2 screen with propietario X MUST appear in X's grid and one created from X's grid MUST carry X as propietario. Propietario stays optional (the desktop `RegisterVehiculo.isRegisterValid` does not check it); a propietario that is not an active transportista answers 422 on that field. The W2 Vehiculo scenarios (S-REF-31) pass unchanged. *Applied in W3-10:* `Propietario` is an inline `lookup` (`FormBuscarAnexo(..., "6")`: filters `Codigo`, `RUC/DNI`, `Descripcion`; columns `CODIGO`, `RAZON SOCIAL`, `RUC/DNI`) over the transportistas with `estado` true (`beanAnexoImp("6", "", "A", id, "")`: the active ones); the entry joins the razón social (`transportista`) and the RUC (`transportista_ruc`) for the list column and the FormBuscarVehiculo filters, and declares `id_marca` / `id_modelo` as exact `lookupFilters`. The list column is `Propietario` and the field sits after `Peso(KG)`. The seed gives vehiculos 001 and 002 the transportista 1 (RUC `20123456789`) and 003 the transportista 2.

### R-MST-7 Usuario
`usuarios` MUST replace the W2 read-only projection by a writable master whose rows remain the `users.json` records (R-AUTH-10). Fields, validation order and messages (entity `un usuario`, lowercase; `{modo}` as above):
1. `id_trabajador`* `lookup` over `trabajadores` (BuscarTrabajador, label `Trabajador`): `Para {modo} un usuario, debes especificar un Trajador.` (spelling kept). The register shows the trabajador name and its `Cargo` (tipo de trabajador) read-only once chosen.
2. `usuario`* (`Nombre de Usuario`, max 50): `Para {modo} un usuario, debes especificar su nombre.`
3. `clave`* password with confirmation (R-CRUD-17; `Contraseña`, max 20): `Para {modo} un usuario, debes especificar su clave.`
4. Flags `Escritorio`, `Web`, `Contable` and `Habilitado`, all default OFF on INSERT (the desktop `newRegister` unchecks them: a new user can log in only after an administrator ticks `Habilitado` and `Escritorio`).
`nombre` (the `usuarios` lookup display) MUST be derived from the chosen trabajador's `nombre`, keeping the W2 row shape `{ id_usuario, usuario, nombre }` (R-MST-17). The stored flags follow `users.json`: `flaghabilitado` `A` enabled / `D` disabled (the desktop stores `H` / `D`; **[INFERRED]** the mock uses its own `A` convention, R-AUTH-4) and `flagEscritorio` / `flagWeb` / `flagContable` `S` / `N`. The legacy `modificar`, `eliminar`, `insertar` user flags are hidden in the desktop and are stored as `N`. The tenants of a new user MUST be the session tenant. A duplicate `usuario` within the tenant MUST answer 409 `DUPLICATE` on `usuario` **[ASSUMPTION]** with the NEW text `El nombre de usuario ya existe.` (the desktop message comes from a stored procedure not in the repository; the login needs the name to be unique). DELETE is the logical delete of R-MOCK-7 and also removes the user's series authorizations (R-MD-7). CLONE copies the fields except the code and the password **[DEVIATION]** (the desktop copied the decrypted password). The list toolbar has the extra `Autorizar Series` action (R-PRM-6). The desktop `Nuevo Trabajador` button (`cbNuevoTrabajador`) is not ported **[ASSUMPTION]** (the "create related" exclusion of R-REF-12). *Applied in W3-11b:* the desktop bean field `nombre` is the LOGIN name (`RegisterUsuario.executeInsert` `setNombre(txt_Nombre)`), which the web calls `usuario`; the lookup `nombre` is copied from the trabajador by the server on every write (`derive` with `fromRef`, D15), the trabajador must be active (`estado` on; a deactivated or retired one is a 422 on `id_trabajador`), `Cargo` is the tipo of the picked trabajador filled on the pick (`fill` + `fillReadOnly`, a stored copy like the Vendedor ones), the checkboxes `Habilitado`, `Escritorio`, `Web` and `Contable` are booleans whose stored flags the server derives (a body cannot write the flags or the legacy `modificar`, `eliminar`, `insertar`, stored `N`), the next id is the next integer over every tenant, and editing a seeded user (which has no trabajador) requires picking one, since `id_trabajador` is required.

### R-MST-8 Usuario credentials
On INSERT and CLONE the password and its confirmation MUST be required. On UPDATE a blank password MUST keep the stored one **[DEVIATION]** (the desktop displayed the decrypted password and required it again; the server never returns it, R-MOCK-23). A password longer than 20 characters MUST be rejected by input (S-CRUD-14) and by the server (422 on `clave`). A confirmation different from the password MUST block submit with an error on the confirmation field and the server MUST answer 422 on `clave_confirmacion` for a body whose confirmation differs. No list, get, lookup or error response MAY ever contain the password (R-AUTH-12). The desktop `Mostrar caracteres` toggle is ported as a show / hide control of the field.

### R-MST-9 Vendedor
`vendedores` MUST be one anexo of tipo 8 built from a trabajador:
- `Cargar Trabajador` (button `Buscar`) opens the PanelCargarTrabajador picker (R-LKP-7); the picked trabajador fills `Nombres`, `Dirección`, `Numero` (its DNI), `Telefono Fijo`, `Telefono Movil` and `Codigo Trab.`; `Nombres`, `Dirección` and `Numero` are filled only by the pick and are read-only in every mode **[DEVIATION from "then"]** (the desktop never lets `Nombres` be typed and disables the other two once loaded; a register whose `Nombres` could be typed would defeat `Debe elegir un trabajdor`). The lookup box is `Codigo Trab.` itself (its code is the sixth filled value, the description beside it is the trabajador name) and clearing or editing the code empties the five copies. In every mode but INSERT the picker is disabled (**Applied in W3-9:** declared as `fill`, `fillReadOnly` and `readOnlyOn: [UPDATE]` of the lookup field, R-REG-13).
- Fields: `Tipo de Documento` (default DNI, id `01`; **[DEVIATION]** the desktop hardcodes id `01` on save and drops the last tipo of the combo; the selected tipo is stored and no entry is dropped), `Numero` (max 8 for DNI, 11 for RUC), `Nacionalidad` default `PERUANA`, `Credito` and `Contado` checkboxes (`Contado` default checked, `Credito` unchecked), `Comentario` (textarea, optional **[DEVIATION]**: the desktop shows it but never saves it; it is stored, max 500 **[ASSUMPTION]**). **Applied in W3-9:** the tipo is required (`Para {modo} un Vendedor, debes Seleccionar un Tipo de Documento.`, **[INFERRED]** wording: the desktop combo has no blank entry), the nacionalidad is required with the same style, the code is padded to ten, the stamp is the session user (tenant scope, `mantVendedor`), `Credito` / `Contado` are booleans (the desktop stores S / N), `Numero` has no minimum (`IntegerDocument(8|11)`), the modes are INSERT, UPDATE, DELETE and DETAIL, and the list keeps the common `Código` header of the reference catalogs for `COD`.
- The only validation is a chosen trabajador: `Debe elegir un trabajdor` (spelling kept), shown on the `Nombres` field.
- It has the shared activation tab (`Activación de Vendedor`) and a derived `Estado` (R-ANX-6, R-ACT-5). Its list columns are `COD`, `NOMBRES`, `DNI`, `DIRECCION`, `TELEFONO`, `CREDITO`, `CONTADO`, `ESTADO`. DELETE cascades to the activation rows (R-MD-7).
- A vendedor MAY be referenced by W4 sales; no uniqueness of the trabajador is applied **[ASSUMPTION]** (procedure not in the repository).

### R-MST-10 Cliente (general)
`clientes` MUST be the identity block of R-MST-2 (entity `un Cliente`; no default tipo; messages `Para {modo} un Cliente, debes ...`) plus:
- `id_clasif_cliente`* select over active `clasif-clientes` (`Tipo Cliente`, first option `--- Seleccione Tipo ---`): `Para {modo} un Cliente, debes Seleccionar un Tipo de Cliente.`, checked after the razón social and skipped when the selected tipo de documento has abreviatura `OTROS` (**[INFERRED]** no seeded tipo is `OTROS`).
- When the company parameter `IS_CLIENTE_CONDICION_PAGO` is true: `Condicion Pago` select (`CONTADO` / `CREDITO`) and `Numero de dias` (digits, max 3; enabled only for CREDITO; reset to `0` on every change of the condición); a blank número de días blocks submit with `Ingrese numero de Dias` (checked last). The condición is stored as `flag_contado` / `flag_credito` `S` / `N` and the días. **[INFERRED]** the values of the desktop `CondicionPagoEnum`.
- `Credito` and `Credito Temp` totals (read-only, default `0`) shown only with the credit tabs (R-MST-12).
- Tabs, in order: `General`, `Activación de Cliente`, `Direcciones`, `Sustitutos` (param), `Credito` and `Credito Temp` (param), `Padrones`, `Contactos`, `Cuentas`. The list columns include `COD`, `T_PERSONA`, `RAZON SOCIAL`, `PATERNO`, `MATERNO`, `NOMBRES`, `RUC/DNI`, `DIRECCION`, and, with the parameters, `CANT_SUST`, `CONDICION PAGO`, `NUMERO DIAS`.
- The padrón flags are derived (R-ANX-8). The client row for the picker consumers (BuscarCliente, FormClienteBuscar) is this master.
- **Applied in W3-16a:** the modes are INSERT and UPDATE (the panel has no clone or detail handler and `executeDelete` returns false); the stamp is the session user only (`mantCliente` parameter 23), tenant scope; the tipo anexo `2` and the code width 10 are [INFERRED] as the Proveedor's (`FormAnexoPadron(..., 2, ...)` is the only evidence). The desktop selects the FIRST tipo de cliente when it loads the combo (`setSelectedIndex(1)`); [DEVIATION] the web register opens on `Seleccione` so the sentence stays reachable. The tipo de cliente is required only while the tipo de documento is one of the offered ones (DNI, CE, RUC: `requiredWhen` over the ids, because no seeded tipo is `OTROS`, [INFERRED]); it is checked after the razón social and before the nacionalidad (`Para {modo} un Cliente, debes Seleccionar un Tipo de Cliente.`). The condición de pago lives on the `General` tab (not a tab of its own) behind `IS_CLIENTE_CONDICION_PAGO`: the select offers the blank item, CONTADO and CREDITO ([DEVIATION] the desktop combo also lists OPERACION_BANCARIA and TARJETA but `saveCondicionPagoCliente` files only CONTADO and CREDITO, so the web offers those two), the días field is labelled `Numero de dias` (the desktop label says `Condicion Pago` twice), is an integer of three digits, disabled except for CREDITO, shown `0` on opening and after every change of the condición, and `Ingrese numero de Dias` is the LAST check; the condición is stored as `condicion_pago` plus the derived `flag_contado` / `flag_credito` `S` / `N` (`saveCondicionPagoCliente` writes them on the anexo row) and `numero_dias`. The list shows `T_PERSONA`, `RAZON SOCIAL`, `PATERNO`, `MATERNO`, `NOMBRES`, `RUC/DNI`, `DIRECCION` and, with `IS_CLIENTE_CONDICION_PAGO`, `CONDICION PAGO` and `NUMERO DIAS` (the code column keeps `Código`; the `AP`, `AR`, `EX` flags and `CANT_SUST` come with W3-17). The picker field names are the real ones (`descripcion`, `numero_doc`, `id_clasif_cliente`); the padron flags and `cant_sust` are no longer gaps since W3-17.
- **Applied in W3-17:** the General tab also shows the three read-only flags `A Percepcion`, `A Retencion` and `Exceptuado` (the desktop checkbox order; derived by the `padron` rule from the active rows, R-ANX-8) and, with `IS_CLIENTE_CREDITO`, the read-only totals `Credito` and `Credito Temp` (number fields owned by an `aggregate`: the server ignores a body value and adds the sum to every answer; the register shows the sum of its grid, pending rows included). The list adds `AP`, `AR`, `EX` (Sí / No) after `DIRECCION` and `CANT_SUST` (with `IS_CLIENTE_SUSTITUTO`). The Padrones tab is always present, after the credit tabs and before Contactos. [DEVIATION] the desktop stored the two totals on the parent (`mantCliente` parameters 20 and 21, read back with `getLineaCred`); the web derives them from the rows, so a legacy total that differs from the rows is not kept.

### R-MST-11 Cliente child grids: Direcciones, Contactos, Cuentas
- **Direcciones** (`Agregar Direccion`, kind `deactivate`): `Departamento`, `Provincia`, `Distrito` (the ubigeo cascade of R-LOC-4, as one cascade), `Zona` (select over active `zonas` of the chosen distrito) and `Direccion` (U). Order and messages: `Debes Seleccionar un Departamento.`, `Debes Seleccionar una Provincia.`, distrito `Debes Seleccionar un Distrito.` **[DEVIATION]** (the desktop says `un Almacen`), `Debes Seleccionar una Zona.` (only when the parameter `IS_DIRECCION_CLIENTE` is false; with it true, the default, the zona is optional and the ubigeo cascade offers every ubigeo, with it false the cascade offers only ubigeos having an active zona, `filter { has: 'zonas' }`, **[INFERRED]** from `loadUbigeo(..., !IS_DIRECCION_CLIENTE)`), `Debes Ingresar Direccion.` Grid: estado, distrito, zona, dirección. `Quitar`: `Direccion ya Esta desactivada`, `Desea Quitar Direccion?`, `Para quitar una direccion primero debe seleccionar la fila.` (title `Quitar Direccion`). **Applied in W3-16b:** the dialog sentences use the `dialog` message style; the departamento and provincia are client-only levels (the server stores the distrito in `id_ubigeo` and refuses a ubigeo that is not a distrito), the zona must belong to the distrito, and the zona requirement and the cascade filter are `byParam` overrides of `IS_DIRECCION_CLIENTE` false (R-REG-17).
