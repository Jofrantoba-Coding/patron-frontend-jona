# Spec: softcommerce-catalog-registry

One declarative registry entry describes a catalog; the CRUD templates, the HTTP mock and the in-browser mock all consume the same entry. Adding a catalog never needs new template, route or service code.
Marker legend: **[ASSUMPTION]** = working assumption, easy to revise.

## Requirements

### R-REG-1 Single declarative entry
Each catalog MUST be fully described by one registry entry plus its seed JSON, `menu.json` node and `permissions.json` grant. The registry MUST be the only place where field rules, refs, unique keys, joins, modes and defaults are written; the UI config, `formRegistry`, and both mocks MUST derive from it.

### R-REG-2 Entry contents
An entry MUST declare: `slug` (path `/v1/{slug}`), `idKey`, `codeWidth` (zero-padded width of the server code, 0 = unpadded; the only code-width declaration), `entity` (label with article, used in messages), `scope` (`tenant`, `empresa` or `shared`), `seed`, `fields`, `columns`, and `messages.style` (`M1`, `M2`, `MS`, `label` or `w1`). It MAY declare `formId`, `title`, `menu` (`{ parent, label }`), `section` (storage section when the route slug differs), `optionLabel` (display for the options endpoint: one field name, or a list of field names joined with " - ", empty parts left out; default `descripcion`), `project` (a closed set of seed projections for a tenant, readOnly, `seed: null` entry, for example `users` for `usuarios`), `readOnly`, `modes`, `stamp` (session-filled fields, `id_usuario` and/or `id_empresa`), `refs`, `joins`, `unique` (`{ fields, includeEmpresa?, errorField, message }`), `validation` (declared step order), `constants`, `derive`, `rules` (named rules), `lookupFilters` and `compat`. A field MUST declare `name`, `kind` (`code`, `text`, `number`, `boolean`, `date`, `select`, `options`) and `label`, and as needed: `required`, `max`, `minLen` (plain minimum length), `maxWhen` / `minLenWhen` (lengths chosen by a predicate: `[{ when: { field, in }, len }]`, the first match decides, `len` never above `max`; both only on `text`), `compose` (target = join of fields), `normalize` (a list of `upper`, `lower`, `digits`, `padLeft:n`), `default` (a value, `today`, or a per-mode map; a per-mode default overrides a cloned value), `blankToDefault`, `readOnlyOn` (modes), `options` (static, with `display`), `source` (`{ catalog, where? }`), `dependsOn` (a list of `{ field, filterKey }` parents), `defaultOption: 'first'`, `transient`, `restoreFrom: { field, prefixLen }` and `filter: { has }` (only on a `select` over `ubigeo`, which the UI renders as the W1 departamento > provincia > distrito cascade; `restoreFrom` is declared once on that select, `field` names a field or a join `as` that carries the stored ubigeo code, cut to `prefixLen` characters; `transient` keeps the select out of the server: never stored, validated or checked as a parent; `filter` is sent with every level request), `clearsOnChange` (fields cleared when this one changes), `scale`, a value range (`range: { min, max }` for an integer, where `max` is the digit count and `messages.range` is then required; `min` / `exclusiveMin` for a decimal, where `scale` only marks it as decimal and caps nothing), `visibleWhen`, `enabledWhen`, `requiredWhen` (each `{ field, in: [...] }`, evaluated by one shared predicate evaluator on client and server), `notFuture`, `afterField`, and message attributes `msgLabel`, `article`, `message`, `messages`. `rules` is a list of `{ name, params? }`: `params` rename the fields the rule reads and carry its constants (for `docIdentidad`: `tipo`, `numero`, `paterno`, `materno`, `nombres`, `razon`, `sexo`, the tipo ids `dni` and `ruc`, and `persona`, the name of a stored-only flag column); rule hooks take `(values, params)`. `constants` and `derive` target stored-only columns: a `constants` key, a `derive` target or a rule `persona` column MUST NOT share a name with a field, with each other or with another stored-only column, and a body value for them is never read. Behavior that declarations cannot express MUST use a closed set of named pure rules; Wave 2 defines only `docIdentidad` (Chofer, Socio) and the lookup filters `ubigeoChildren` and `ubigeoHasActive`. Derived lookup filters are declared on the target entry as `lookupFilters` (`via`, `exists` or `rule`).

### R-REG-3 Consistency across consumers
A consistency test MUST prove that, for every entry, the UI config, the HTTP mock and the in-browser mock expose the same fields, required flags, max lengths, refs, unique keys and joins. Drift in any consumer MUST fail the test.

### R-REG-4 Registry validation at load
The registry MUST fail fast at load (before any request) when: two entries share a `slug` or `formId`, or an `idKey` (the single exemption: entries over a W1 storage section, `seed: null`, such as `empresa` and `punto-venta`, keep the W1 row key `id` and MAY share it; a seeded entry MAY NOT); a `source` or ref points to an unknown or missing catalog; a `dependsOn`, `visibleWhen`, `enabledWhen`, `requiredWhen`, `afterField`, `unique` or `joins` clause names an unknown field; a dependent chain is cyclic; a named rule or `validation` step names an unknown rule, field, unique index or ref; a `scope` is not one of `tenant`, `empresa`, `shared`; or a field kind lacks a required attribute (for example `select` without `source`, `options` without values, `number` without `scale`).

### R-REG-5 Automatic seed registration
Seed JSON files declared by `entry.seed` (`data/catalogs/<seed>.json`) MUST be registered automatically in both sources; no hardcoded seed or tenant-section lists may remain. Store sections are derived from `scope`: `tenant` and `empresa` entries are stored per tenant, `shared` entries once globally. A tenant without a seed for a per-tenant catalog MUST get an empty dataset; a malformed seed MUST fail at load.

### R-REG-6 Refs
Refs MUST be derived from the field `source` (`catalog` plus static `where`, for example `active` or `persona:true`) and the `dependsOn` parents: exists, `activeOnly` (default true), belongs-to-parent, and `where` apply to ref validation exactly as they apply to the options query. The mock MUST validate every ref on create and update; the UI MUST build the select from the same declaration.

### R-REG-7 Composite unique keys
`unique` MUST declare `{ fields, includeEmpresa?, errorField, message }` (the session empresa is part of the key only with `includeEmpresa`). A violation MUST be reported as a 409 `DUPLICATE` rule error mapped to that field (R-MOCK-11). The record being updated MUST NOT conflict with itself. Logically deleted records MUST NOT count. **[ASSUMPTION] logically deleted records are ignored by uniqueness.**

### R-REG-8 Joins
`joins` MUST declare display columns resolved from refs (`{ as, ref, display, prefixLen? }`). Every `options` field additionally yields a `<name>_label` key on list and get (R-MOCK-14). Both sources MUST return the same joined keys on list and get. A join over a missing or inactive target MUST yield an empty string, never an error.

### R-REG-9 Menu and permissions consistency
Every entry with a `menu` node MUST appear in `menu.json` with its `formId`, and `permissions.json` MUST grant the 13 permission flags for that `formId`. A consistency test MUST fail when the registry, `menu.json` and `permissions.json` disagree.

### R-REG-10 Supported modes
An entry MAY restrict `modes` to a subset of INSERT, UPDATE, DELETE, DETAIL, CLONE (default all five). `modes` MUST filter the toolbar actions before permission gating (unsupported actions are not rendered; shortcuts and double-click are inert), and the mock MUST reject a write outside `modes` with 405 `MODE_NOT_SUPPORTED` and the error shape. This code is distinct from `METHOD_NOT_ALLOWED` (R-REG-11).

### R-REG-11 Read-only lookups
An entry flagged `readOnly` MUST expose only `GET` list and `GET` by id. Any write route MUST answer 405 `METHOD_NOT_ALLOWED` with the error shape (distinct from `MODE_NOT_SUPPORTED`, which applies to writes outside a writable entry's `modes`). Such entries MUST NOT appear in the menu.

### R-REG-12 Localidad migrates without behavior change
The W1 Localidad catalog MUST be re-expressed as a registry entry with identical external behavior, carrying a `compat` block (`messages: 'w1'`, `serverOptional: ['direccion']`) and `validation: ['id_empresa','descripcion','id_ubigeo','direccion']`; the consistency test MUST exempt only `serverOptional`; all W1 suites MUST pass unchanged. The legacy W1 routes `GET /v1/empresas` and `GET /v1/puntos-venta?id_empresa=` MUST stay byte-identical to W1. The Wave 2 Empresa and PuntoVenta entries use the route slugs `empresa` and `punto-venta` with a `section` equal to the existing W1 storage section, so both route families see the same data. Because the W1 rows are `{ id, name }`, the Empresa `Nombre` and the PuntoVenta `Descripción` are stored under `name` (labels and messages unchanged), and the W1 routes project `{ id, name }` / `{ id, name, id_empresa }` in that key order and hide `activo: false` rows, so the extra Wave 2 fields never leak into W1 bodies.

### R-REG-13 Extended kinds and attributes
In addition to the field kinds of R-REG-2 (`code`, `text`, `number`, `boolean`, `date`, `select`, `options`) a field MAY have kind `password`, `textarea` or `lookup` (softcommerce-crud-templates R-CRUD-17..19). A `password` field MUST declare `max` and MAY declare `confirm` (default true). A `textarea` MAY declare `rows` (a positive integer, default 4; rejected on any other kind) and `max`; the core (validators, normalization, the UI validation) treats it as a `text`, and the UI config of a `textarea` is a `text` field with `multiline: true` and `rows` (**Applied in W3-9**). A `lookup` MUST declare `source` (`{ catalog, where? }`, the same shape as a `select`), the `search` fields of the picker, its `columns`, its `filters` (R-LKP-2), and MAY declare `display` (the joined display key), `pickLabel` and the `dependsOn` parents of R-CRUD-12. **Applied in W3-9:** a `lookup` MAY also declare `fill: { targetField: sourceKey }` (each target a field of the entry other than the lookup itself, each key a field or joined display key of the source; a pick, and a typed code that resolves, copies the row into the targets, and clearing or editing the code empties them), `fillReadOnly: [targetField]` (a subset of the `fill` targets, shown read-only in every mode) and `readOnlyOn` (modes where the picker is disabled); `fill` and `fillReadOnly` are rejected on any other kind. The server never copies: it stores the body (S-MST-18). **Applied in W3-16b:** a `select` MAY declare `fillLabel: { target, unless? }` (target a field of the entry other than itself; `unless` a list of option ids): choosing an option copies its NAME into the target and the ids in `unless` leave it empty to be typed (the banco OTROS of a Cliente cuenta); client side like `fill`, the server stores the body; rejected on any other kind. The messages `style` MAY be `dialog` (the bare sentences of a child dialog: `Debes Seleccionar un Distrito.` for a select, `Debes Ingresar Direccion.` for a text; a field `message` still wins). A `lookup` MUST be validated as a ref like a `select` (R-REG-6). The extended kinds are available to the UI config, `formRegistry` and both mocks from the same entry (R-REG-1).

### R-REG-14 Child entries
An entry MAY declare `children`: a map from the child name (the nested route segment, R-MOCK-19) to a child entry with its own `fields`, `columns`, `refs`, `joins`, `unique` (R-MD-6, among active siblings), `validation`, `messages`, `removal` (`deactivate` or `delete`, R-MD-4), `entry` (`dialog` or `inline`, R-MD-3), `tab` (the register tab title, R-MD-1), an optional `gate` (R-REG-17), an optional `quitar: { none, confirm, already }` (the grid messages of Quitar, R-MD-4: no selected row, the desktop question, a row already deactivated; a non-empty text each, defaults `Seleccione Fila.` and `Fila ya Esta desactivada`, no question when `confirm` is absent) and an optional `initial` (stored field values of the first row the server creates for every new parent whose body inserts none of that child, R-MD-9; the keys MUST be child fields; not available on a store child). `children` is a map or, to let the load check a repeated name, a list of `{ name, ...def }`; `removal` also accepts `none` (no delete, R-ANX-1 activaciones). A child MUST NOT declare its own `slug`, `menu`, `formId`, `scope` or permissions: it inherits the parent's (R-REG-19). A child field `name` MUST NOT collide with the parent's stored-only columns or with the reserved child keys (`id`, `estado`, `op`). A child MAY declare `store: { entry, key }` when it is a filtered view of another entry's storage section (Vehiculos over `vehiculos` keyed by `id_anexo_empresa_transportista`; Series over `usuario-correlativos` keyed by `id_usuario`): its rows live in that entry's section and its seeds stay with the owning entry. A store child takes the fields, `unique`, `joins`, `validation` and columns of the owning entry (declaring `fields`, `unique`, `joins`, `validation` or `refs` of its own is a configuration error; `columns`, `tab`, `removal`, `entry` and `gate` may be given), has `seed: null`, keys its rows on the owner's `idKey`, and links them to the parent through `store.key` (a stored column of the owner; the nested write sets it). Other child seeds are declared inside the parent's seed rows under the child name **[ASSUMPTION]**. The registry exposes the expanded children as `registry.childEntries` (slug `parent/name`, resolvable through `bySlug` only; they are not in `entries`). The consistency test of R-REG-3 MUST cover every child: UI config, HTTP mock and in-browser mock MUST expose the same child fields, required flags, max lengths, refs, unique keys, removal kind and joins; drift MUST fail the test naming the parent, the child and the field. **Applied in W3-7:** a child `entry` may be `none` (no Agregar: the rows come from the actions, as the activation history); the anexo child `activaciones` uses `removal: none`, `entry: none` and `initial: { motivo_activacion: INICIO }`.

*Applied in W3-10 (R-REG-14, store child view):* a store child MAY declare `entryFields: [{ name, message? }]`, a pick of the owner's fields (never the code or the parent key) that the entry of its parent shows, in that order, each with an optional required message; the child entry checks them first in that order and then what the owner still checks, without the ref check of the parent key (the nested route binds the row). Without `entryFields` the child shows every owner field. `entryFields` on a child that is not a store child is a load error. *Applied in W3-10 (R-REG-6):* a `lookup` field that an explicit `validation` leaves out is still checked as a ref, as a trailing step (a `ref` step when the validation already uses `ref` steps); the declared order of the desktop checks and the `validation` list itself stay as written.

### R-REG-15 Row actions
An entry or a child MAY declare `actions`: a list of `{ id, label, placement, flag, enabledWhen, dialog?, kind, confirm?, server?, rule? }` (softcommerce-row-actions R-ACT-1). `flag` MUST be one of the 13 permission flags (default `modify`); `placement` is `list-toolbar` or `register` on an entry (default `register`) and `child` on a child; `kind` is `deferred` or `immediate`. `enabledWhen` is `{ modes?, selection?, row?, noRow? }`: `modes` lists register modes, `selection` needs a selected row, `row` is a `{ field, in }` condition on the selected row and `noRow` one no row of the grid may meet (child actions only); the condition fields MUST be known fields of the entry or child (a child also has `id` and `estado`). An `immediate` action MUST name its `server` action (R-MOCK-22) and a `deferred` one the client `rule` that changes a pending row; neither may name the other. A `dialog` is `{ title, fields }`, its fields checked like the fields of any entry. The ids are unique per owner and `actions` is reserved. The templates MUST render actions from this declaration only. **Applied in W3-7:** an entry action may have the placement `api` (served by the endpoints, never rendered: the anexo `activar` / `desactivar` of S-MOCK-47..49), and an action may declare `params` (an object of constants the named rule reads, such as the entity word of the anexo messages).

### R-REG-16 Search declaration
An entry MAY declare `search`, the list of field names (or joined display keys) searched by the free-text `q` parameter (R-MOCK-20) and offered as picker filters. Every name MUST be a known field or join; the per-field contains filters of R-MOCK-9 MAY name any field or join of the entry.

### R-REG-17 Company-parameter gates
A field, a tab, a child or an action MAY declare `gate: { param, in? }`: it exists only when the session company parameter `param` is true (or, with `in`, equals one of the listed values). `param` MUST belong to the closed set of the `GET /v1/params` keys (R-MOCK-24) and hold a boolean (`PORC_IGV` and `INICIO_ACTIVIDADES` are values, never gates, D25); `in`, when given, MUST be a non-empty list. A `$params.X` field default MUST name a params key (D27b). In W3-4b the server applies the gate to children (nested routes 404, composite body ignored); **Applied in W3-16a:** the server also applies it to FIELDS: a gated-off field is left out of `pickWritable` (a body value is ignored and stored nowhere, an UPDATE keeps what was stored while the parameter was on), gets no default (`withDefaults`) and is not validated or required (`validateRecord`), and the UI register drops it (`UiMasterRegisterImpl`, so it is neither drawn, validated nor sent). A LIST COLUMN MAY declare `gate` too (validated at load like a field gate; the list leaves it out while the parameter is off, and with no session no gate is open: CONDICION PAGO and NUMERO DIAS of the Cliente). **Applied in W3-16b:** a field MAY declare `byParam: { param, in?, set }` (`param` and `in` follow the gate rules; `set` is a non-empty object of `required` and, for the ubigeo cascade, `filter`): while the parameter holds a listed value (`in: [false]` matches a false parameter) the overrides replace the declared ones, on the server (`effectiveField` before the field check) and in the UI (the master register and its child dialogs take the effective field). The Cliente direccion uses it: the zona is required and the cascade filtered `{ has: 'zonas' }` only with `IS_DIRECCION_CLIENTE` false. **Applied in W3-17:** an entry MAY declare `aggregate: [{ as, child, op: 'count' | 'sum', field?, where? }]` (D27a): `child` a declared child, `field` (required for `sum`) a field of that child, `where` exact-text column filters (`{ estado: 'A' }` is the active rows), `as` unique and either free or a `number` field of the entry; a logically deleted row never counts and a sum is kept to cents. The server adds each `as` to every answer of the entry (list, get, write responses) and never lets a body write it; the master register shows, for an `as` that is one of its fields, the value of its grid (persisted and pending rows) with the same pure functions (`core/aggregate.js`); a list column may show it (`CANT_SUST`). A child MAY be `entry: 'picker'` with `pick: { picker, field, message, copy? }` (`Agregar` opens the named picker, a pick adds a row whose `field` is the picked id and whose `copy` columns are copied from the picked row, `message` is the host veto text) and MAY be `reactivable` (an `A` op with estado `A` reactivates a deactivated row). **Applied in W3-18:** a gate MAY add `or: [param, ...]`, more boolean params that pass the same test, any one of which opens it (the Item `Composicion` and `Funcion`: `ISBOTICA` or `IS_BOTICA_SIN_LOTE`); each follows the rules of `param`. A field MAY declare `follows: { field, map?, otherwise? }` (D27b): its value is computed from another field of the entry, a copy of it without `map`, else the `map` entry for the text of the source, else `otherwise` (a `$params.X` value resolves against the company params; a `$params.X` default is resolved the same way in the register). The server applies it before validating (`withFollowed`) to a LOCKED follower, one that is read-only in INSERT and UPDATE (`readOnlyOn`) or disabled by its `enabledWhen`, so a body value never wins; an editable follower keeps the body value. The register applies it on every edit of the source (`changeField`). `follows.field` must name another field and a token must name a params key. An entry MAY declare `generalTab`, the title of the first register tab when it is not `General` (a non-empty text no layout or child tab uses; the Item says `Datos de Item`), and a register with a `generalTab` is the master register even with no children. **Applied in W3-19:** a child MAY declare `closeDate`, the name of a row column (a non-empty text; it need not be a field of the dialog): a deactivation of a persisted row (a composite `A` op with estado `D`, or the nested DELETE of a `deactivate` child) sets that column to today on the server (the Item almacen closes its `F_FIN`, `desactivarAlmacen`).
A gated element MUST be absent (not hidden) from the UI when the gate is off, MUST be neither validated nor required, and the server MUST ignore a body value for a gated-off field and answer 404 with the error shape to nested routes of a gated-off child.

### R-REG-18 Promoted lookups
The entries `usuarios` and `trabajadores` (promoted in W2 as read-only lookups, R-REG-11) MUST become writable masters with their menu leaf and formId (`mi_usuario`, `miTrabajador`), declaring the modes of softcommerce-masters R-MST-1. They MUST keep their `slug`, `idKey`, `optionLabel` (`nombre`), the lookup row shape and the filters of R-MOCK-16, so every W2 consumer (UsuarioCorrelativo, TrabajadorPuntoVenta) stays unchanged. The `usuarios` entry is backed by the `users.json` store that the login also reads (softcommerce-auth-session R-AUTH-10): the W2 `project: 'users'` projection MUST be replaced by a read-write backing of that store (still tenant-filtered, still no password key, R-MOCK-23) **[ASSUMPTION]** with no copy of its rows; the `trabajadores` seed grows to the full master fields. The R-REG-11 rule "read-only entries MUST NOT appear in the menu" no longer applies to them. *Applied in W3-11b:* `backing: 'users'` (`registry/backings.js`, a closed set of `{ rows, all, insert, present, stored, seed }`; it needs `seed: null` and scope `tenant`, and excludes `project`) gives the entry the LIVE tenant records of `store.shared.users`; the seed is normalized at store load (text ids, `clave` replaced by the salted `clave_hash`, missing `flagWeb` / `flagContable` `N`, `users.json` unchanged) and the login returns the id as a number as before. The W2 `project` mechanism and its `PROJECTIONS` stay in the schema because the W2 `schema.project.spec` pins them; no registry entry uses them any more. A `derive` rule may be `{ target, fromRef: { field, key } }` (the column copies `key` of the row a select or lookup `field` points to; server-owned, never written by a body), and such a target is a valid `optionLabel`.

### R-REG-19 Menu, permissions and custom screens
Every entry with a `menu` node MUST appear in `menu.json` with its `formId` and be granted the 13 flags in `permissions.json` (R-REG-9); children and actions MUST NOT have their own node or formId and MUST be gated by the parent's flags (R-ACT-2). The two Wave 3 screens that are not registry catalogs, `mi_SeguridadPerfil` (perfil permissions) and `miAccionSocio` (Socio acciones, a custom resource, R-MOCK-26), MUST be listed in a custom-screen list read by the same consistency test: each MUST appear in `menu.json` with its `formId` and in `permissions.json`. The test MUST fail naming the `formId` when any of them disagrees. **Applied in W3-13:** the list is `CUSTOM_SCREENS` in `test/catalogs/menuPermissions.ts` (checked by `customScreenProblems`, node under `mnGenerales`, label `Seguridad - Perfil`, grant with only `close`); `miAccionSocio` joined it in W3-20 (node `Acciones de Socio` under `mnGenerales` [INFERRED label], grant with only `close`).

### R-REG-20 Registry validation at load (Wave 3)
In addition to R-REG-4 the registry MUST fail fast at load, before any request, when: a child `unique`, `refs`, `joins`, `columns` or `validation` names an unknown field; a child `removal` or `entry` is not one of its closed values; two children of an entry share a name or a child name collides with a parent field or a reserved route word (`actions`, `menu`, `permisos`); a `lookup` has no `source` or no `search` fields, or its source is not a registered catalog; a `password` has no `max`; a `gate.param` is not a known params key; an action `flag` is not one of the 13 flags, its `enabledWhen` names an unknown field, mode or key, an `immediate` action has no `server` or a `deferred` one no `rule`, or its placement is not for its owner; a `search` name is unknown; a lookup or select chain is cyclic.

### R-REG-21 Named rules in Wave 3
The closed set of named pure rules (R-REG-2) MUST be extended only with: `docIdentidad` applied also to Banco, Transportista, Cliente and Proveedor (the Wave 2 rule with its params, unchanged, plus `entity` for the message wording, R-MST-2); `activacion` (the single-active-row rule and derived `estado` of R-ANX-5 / R-ACT-5); `padron` (the same-padrón and incompatibility rules of R-ANX-7); and the lookup filters `ubigeoChildren` and `ubigeoHasActive` reused by the Cliente direcciones. Each MUST be a pure function of its inputs, run by both mocks and, for client-side hooks, by the UI, with identical results.

## Scenarios

**S-REG-1 one entry drives all consumers** — Given a new minimal entry (one required text field) plus seed, menu and permissions, When the app starts, Then the list and register work against both sources with no other code change.

**S-REG-2 consistency test** — Given an entry whose `max` differs between the UI config and the mock rule, When the consistency test runs, Then it fails naming the catalog and the field.

**S-REG-3 duplicate slug** — Given two entries with the same `slug`, When the registry loads, Then it throws a configuration error before any request.

**S-REG-4 unknown lookup** — Given a `select` field whose `source` is not a registered catalog, When the registry loads, Then it throws a configuration error naming the field.

**S-REG-5 cyclic chain** — Given field A with `dependsOn` B and field B with `dependsOn` A, When the registry loads, Then it throws a configuration error.

**S-REG-6 auto seed** — Given an entry with seed file `aduanas.json` for `demo` only, When the `botica` tenant lists it, Then it returns an empty list and no error; the `demo` tenant returns the seeded rows.

**S-REG-7 malformed seed** — Given a seed file that is not valid JSON, When the mock loads, Then it fails at load naming the file.

**S-REG-8 ref validation** — Given a required ref `id_familia` pointing to `familias`, When a record is created with an unknown id, Then the mock answers 422 with a detail on `id_familia`.

**S-REG-9 unique key excludes self** — Given a record with a unique key, When it is updated without changing the key, Then no conflict is reported.

**S-REG-10 deleted record frees the key** — Given a logically deleted record with key K, When a new record with key K is created, Then it succeeds.

**S-REG-11 joins parity** — Given a catalog with a join, When it is listed from the HTTP mock and from the in-browser mock, Then both return the same joined key and value; an inactive target yields an empty string.

**S-REG-12 menu and permissions consistency** — Given an entry whose `formId` is missing in `permissions.json`, When the consistency test runs, Then it fails naming the `formId`.

**S-REG-13 unsupported mode** — Given an entry with `modes` = `[UPDATE, DETAIL]`, Then the toolbar offers no add, eliminate or clone, and `POST` answers 405 `MODE_NOT_SUPPORTED`.

**S-REG-14 read-only lookup** — Given a `readOnly` entry, When `POST`, `PUT` or `DELETE` is called, Then the answer is 405 `METHOD_NOT_ALLOWED` with the error shape and the data is unchanged (not `MODE_NOT_SUPPORTED`).

**S-REG-15 Localidad unchanged** — Given the W1 Localidad suites, When they run against the registry-driven stack, Then they pass unchanged, and `GET /v1/empresas` and `GET /v1/puntos-venta?id_empresa=1` still answer byte-identically to W1, including after records are written through `/v1/empresa` and `/v1/punto-venta`.

**S-REG-16 unknown named rule or step** — Given an entry that lists `rules: [{ name: "nope" }]` or a `validation` step `{ unique: 3 }` with only one unique key, When the registry loads, Then it throws a configuration error naming the entry.
